# Near-real-time sports action recognition from live video: research report (Oct 31, 2026)

Scope note: everything below is from web sources fetched today. Stars / last-push / license fields come from the GitHub API today. Where I could not verify something, I say so rather than guess. Nothing here is legal advice; license and ToS points are flags for your counsel.

## 1. Language choice

**What the sources say**

- DeepStream's native API is C/C++; the Python bindings (`pyds`) are thin wrappers. Frame access from Python (`get_nvds_buf_surface`) only supports RGBA, requires unified memory on x86, and users report large throughput drops when a Python probe copies frames (30 → 6 FPS on 20 streams in one thread). Sources: [Savant vs DeepStream](https://savant-ai.io/blog/savant-vs-deepstream-what-to-use-when-and-why/), [NVIDIA pyds docs](https://docs.nvidia.com/metropolis/deepstream/dev-guide/python-api/PYTHON_API/Methods/methodsdoc.html), [NVIDIA forum perf thread](https://forums.developer.nvidia.com/t/deepstream-frame-data-garbage-collection-causing-silent-halt-in-multi-process-pipeline/340860), [deepstream_python_apps](https://github.com/NVIDIA-AI-IOT/deepstream_python_apps) (Apache-2.0, 1.9k stars).
- Savant (Apache-2.0, 866 stars, pushed 2026-09) is a Python-first framework on top of DeepStream/TensorRT; vendor claims 80–90% of hand-tuned DeepStream throughput; first run compiles TRT engines for 30–40 min. [Savant repo](https://github.com/insight-platform/Savant), [Savant vs PyTorch](https://savant-ai.io/blog/savant-vs-pytorch-video-analytics-vs-model-training/).
- Rust: inference goes through `ort` (ONNX Runtime) with the TensorRT EP; the `rf-detr-ort` crate reports ~482 FPS FP16 TRT but documents an explicit process-exit workaround for an ORT/TRT destructor segfault. Direct TRT bindings (`trtx`, `baracuda-tensorrt`) are marked experimental/alpha. GStreamer Rust inference plugins need GStreamer ≥1.28. Savant's own blog argues Rust's win is the pipeline plumbing (shared-memory frames across threads, no GIL), not the kernels. [rf-detr-ort](https://lib.rs/crates/rf-detr-ort), [trtx](https://docs.rs/trtx), [gstsmith-rs](https://github.com/zbiljic/gstsmith-rs), [Rust's place in CV](https://savant-ai.io/blog/rust-real-place-in-computer-vision/).
- Go: `gocv` (7.5k stars) wraps OpenCV DNN/CUDA; I found no evidence of TensorRT integration or production real-time inference write-ups. [gocv](https://github.com/hybridgroup/gocv).
- Python: PyAV (BSD-3, 3.3k stars, pushed 2026-10) now has `HWAccel.create("cuda"|"videotoolbox", ...)`, `hwdevices_available()`, `CodecContext.is_hwaccel`; a recent fix stopped network writes from holding the GIL. [PyAV CHANGELOG](https://github.com/PyAV-Org/PyAV/blob/main/CHANGELOG.rst). torchcodec (BSD-3, 1.2k stars) decodes on NVDEC straight into CUDA tensors. [torchcodec](https://github.com/meta-pytorch/torchcodec).
- A general 2026 playbook recommends TensorRT/DeepStream over raw PyTorch and keeping buffers on the GPU from decode to inference. [Fora Soft](https://www.forasoft.com/blog/article/real-time-video-processing-with-ai-best-practices). An older comparison found DeepStream uses ~15% less GPU memory than a Python/PyTorch pipeline. [Medium](https://medium.com/@gyrusai/a-comparison-of-real-time-vision-ai-pipelines-268fc2820e7e).

**Where each wins**

| | Wins | Loses |
|---|---|---|
| Python | Every model in §2 ships as PyTorch; fastest iteration; TRT/ORT engines callable from Python at full speed | GIL forces multiprocess for CPU-bound stages; per-frame Python overhead matters at >4 streams |
| C++ (TensorRT/DeepStream) | Multi-stream density, lowest decode→infer copies | 5–10x dev time; research models need re-implementation; no SoccerNet baselines exist in C++ |
| Rust | Thread-safe pipeline plumbing without GIL; `ort` is usable | TRT bindings immature; no CV research ecosystem |
| Go | Service glue | No inference story beyond OpenCV DNN |

**Common production pattern:** Python orchestration + TensorRT (or ONNX Runtime) engines, GPU decode via NVDEC, frames kept as CUDA tensors; GStreamer/DeepStream (or Savant) only when you need many concurrent streams per GPU. Pixellot is a public example of DeepStream on Jetson in production. [NVIDIA blog](https://blogs.nvidia.com/?p=67151).

**Recommendation:** Python 3.12, PyAV or torchcodec for decode (NVDEC on Linux, VideoToolbox on Mac), TensorRT FP16 engines for detector/pose/ball (ONNX Runtime CoreML EP or MPS on Mac), asyncio + per-stage queues, one process per stream. Revisit Savant/DeepStream only if you need >3–4 streams per GPU; revisit Rust only for the ingest/mux layer.

### 2b. Multi-object tracking

- Generic trackers, all MIT: [ByteTrack](https://github.com/FoundationVision/ByteTrack) (6.8k), [BoT-SORT](https://github.com/NirAharon/BoT-SORT) (1.6k), [OC-SORT](https://github.com/noahcao/OC_SORT) (1.2k, pushed 2026-04), [Deep OC-SORT](https://github.com/GerardMaggiolino/Deep-OC-SORT), [BoostTrack/BoostTrack++](https://github.com/vukasin-stanojevic/BoostTrack) (236, pushed 2026-03). [boxmot](https://github.com/mikel-brostrom/boxmot) bundles them but is AGPL-3.0.
- SportsMOT (HOTA, test): Deep-EIoU 77.2 → +GTA 81.04 → MeMoSORT 82.1 → ARC-SORT 83.04 (training-free, motion-only on CPU, ~50 FPS on laptop RTX 3060, Apache-2.0, ranks 10th on CodaBench Oct 2026). Older CodaLab snapshot top was 85.63. Sources: [SportMamba table](https://arxiv.org/pdf/2506.03335), [GTA](https://arxiv.org/pdf/2411.08216) / [gta-link](https://github.com/sjc042/gta-link) (MIT), [MeMoSORT](https://arxiv.org/pdf/2508.09796), [ARC-SORT](https://github.com/Athlitix/arcsort), [Deep-EIoU](https://github.com/hsiangwei0903/Deep-EIoU) (74 stars, no license), [CodaLab](https://codalab.lisn.upsaclay.fr/competitions/12424), [GTATrack SoccerTrack 2025 winner](https://arxiv.org/pdf/2602.00484).
- SoccerNet Tracking 2023 winner Kalisteo 75.61 HOTA: YOLOX + "TrackMerger v2" (two Hungarian passes on IoU and center distance, Kalman with camera-motion compensation) + MGN re-ID merging. [2023 results](https://arxiv.org/html/2309.06006v1).
- SoccerNet GSR (game state reconstruction, GS-HOTA): 2024 winner Constructor.tech 63.81 (YOLOv5 + DeepSORT run in pitch coordinates + OSNet team-ID on 111 uniforms + 74-keypoint calibration voting). 2025: KIST GSR-1 63.90 (YOLOX + Deep-EIoU + OSNet re-ID + LLaMA-3.2-Vision for jersey/role), Constructor.tech 63.81, lianyou 62.76 (YOLOv12 + optical-flow IOF tracker + CLIP-ReIdent + PnLCalib with radial-distortion correction and temporal smoothing). Baseline 29.01. [2024 results](https://arxiv.org/html/2409.10587v1), [2025 results](https://arxiv.org/html/2508.19182v1), [Constructor paper](https://mlanthology.org/cvprw/2025/golovkin2025cvprw-broadcast/).
- Takeaway: on broadcast sports, the gains come from camera-motion compensation, tracking in pitch coordinates, and re-ID-based tracklet merging, not from the base association rule. Deep-EIoU + GTA or ARC-SORT are the sport-tuned picks; BoostTrack++/OC-SORT if you want MIT and simplicity.

### 2c. Small fast ball detection

- WASB (BMVC 2023, MIT, 204 stars, last push 2023-11): HRNet-based heatmap detector with stride-free stem, SOTA across soccer/basketball/volleyball/tennis/badminton datasets at publication; still the base detector in 2025 work (BlurBall table tennis) and a baseline in RacketVision (2025). [repo](https://github.com/nttcom/WASB-SBDT), [paper](https://arxiv.org/html/2311.05237v2), [BlurBall](https://arxiv.org/html/2509.18387v1), [RacketVision](https://arxiv.org/pdf/2511.17045).
- TrackNet line (badminton/tennis): [TrackNetV3](https://github.com/qaz812345/TrackNetV3) (MIT incl. checkpoints, 322 stars, pushed 2026-09), TrackNetV4 (ICASSP 2025, motion-attention), TrackNetV5 (Dec 2025, motion-direction decoupling; a separate repo of the same name reports F1 98.3 vs V3 97.59), TD-Net 2026 lightweight. [TrackNetV5 arXiv](https://arxiv.org/html/2512.02789v1), [gino6178/TrackNetV5](https://github.com/gino6178/TrackNetV5), [TD-Net](https://link.springer.com/article/10.1007/s11227-026-08237-7).
- MonoTrack (CVPRW 2022, badminton 3D from mono): [repo](https://github.com/jhwang7628/monotrack) (59 stars, no license, 2023). "BallTrack": I could not locate a repo or paper under that name.
- Soccer broadcast ball: an online single-camera filter at ~50 fps with ≤50 frames latency (vs 6 fps offline baseline) [arXiv 2506.07981](https://arxiv.org/pdf/2506.07981). Practical path used by challenge teams: a fine-tuned small detector (MOT4MOT used YOLOv8l for the ball) [MOT4MOT report](https://arxiv.org/pdf/2308.16651); Roboflow ships a ball dataset and `sports.common.ball` tracker [roboflow/sports](https://github.com/roboflow/sports).
- Recommendation: Apache detector (RF-DETR nano / D-FINE) fine-tuned for ball on full frames, WASB-style heatmap on a crop around the predicted ball when detection is lost, constant-velocity Kalman in pitch coords. TrackNetV3/V5 for tennis only.

### 2d. Pose estimation

- RTMPose-m: 75.8 AP COCO, 90+ FPS on i7-11700 CPU, 430+ FPS GTX 1660 Ti (Apache-2.0 via mmpose). [paper](https://arxiv.org/pdf/2303.07399), [mmpose](https://github.com/open-mmlab/mmpose) (8k stars, last push 2025-08).
- RTMO (CVPR 2024, one-stage): matches RTMPose accuracy, faster once ≥2 people under TRT FP16; RTMO-L 141 FPS V100. [paper](https://arxiv.org/pdf/2312.07526), [project](https://github.com/open-mmlab/mmpose/tree/main/projects/rtmo).
- YOLO11-pose (AGPL): an independent 2026 table shows it lower-latency but lower AP than RTMO at S/M; RTMO-L 76.8 vs YOLO11-pose-L 73.3. [arXiv 2609.26590](https://arxiv.org/pdf/2609.26590).
- ViTPose (Apache-2.0): ViTPose-G 80.9 AP; GPU-only; no recent latency numbers. [repo](https://github.com/ViTAE-Transformer/ViTPose).
- Sapiens (Meta): LICENSE file is CC-BY-NC 4.0 → not usable commercially. [repo](https://github.com/facebookresearch/sapiens). DWPose (Apache-2.0, whole-body distilled from RTMPose). [repo](https://github.com/IDEA-Research/DWPose).
- Recommendation: RTMO via mmdeploy → TensorRT for broadcast frames with 10–22 visible players; RTMPose top-down on tracked boxes if you only need the 2–4 players near the ball.

**Temporal action detection:** ActionFormer (MIT) [repo](https://github.com/happyharrycn/actionformer_release), TriDet (MIT) [repo](https://github.com/dingfengshi/TriDet). Both are full-sequence offline designs; windowing works but adds window-length latency.

**Which can run streaming/online?**
- None of the SoccerNet winners were evaluated online, and no report gives inference speed or latency. T-DEED's 100-frame clips (4 s at 25 fps) imply ~2 s best-case lag with a centered sliding window; TAAD/DST are clip-based too.
- E2E-Spot's per-frame GRU head and Baikulov's short frame stacks are the easiest to run causally.
- Purpose-built online methods: MoViNet stream buffer (causal convs, O(1) memory, A0-Stream 4.8 ms int8 on Pixel 4) [paper](https://openaccess.thecvf.com/content/CVPR2021/papers/Kondratyuk_MoViNets_Mobile_Video_Networks_for_Efficient_Video_Recognition_CVPR_2021_paper.pdf), [Kaggle models](https://www.kaggle.com/models/google/movinet); CMeRT (CVPR 2025, online action detection with an explicit latency mask) [paper](https://openaccess.thecvf.com/content/CVPR2025/papers/Pang_Context-Enhanced_Memory-Refined_Transformer_for_Online_Action_Detection_CVPR_2025_paper.pdf); StreamFormer (ICCV 2025, causal attention on SigLIP with KV cache, 68.4 mAP THUMOS RGB) [arXiv](https://arxiv.org/html/2504.20041); distilled streaming ViT (20.3 ms vs 87.9 ms offline teacher on AVA) [summary](https://lacuna.tiptreesystems.com/work/distilling-offline-action-detection-models-into-real-time-streaming-models/wrk_60ffae55f1c2e4d006ba1875a180b79b); an older Simula sliding-window real-time soccer detector [paper](https://home.simula.no/~paalh/publications/files/ism2020-olav.pdf).
- Practical design: a causal "provisional" event from tracking state (ball possession change, ball speed spike, ball crossing the box) within ~200 ms, then a "confirmed" event from a windowed spotting head 2–3 s later.

### 2f. Vision-language models

- The only direct benchmark of VLMs for soccer action spotting is [Zero-Shot Multimodal Event Spotting in Soccer Broadcasts (arXiv 2610.37583)](https://arxiv.org/html/2610.37583): 15-s clips rendered as a 15-frame storyboard + Whisper commentary. mAP@5s / F1 / cost per match: GPT-5.5 76.24 / 72.02 / $18.01; GPT-5.6 Luna 67.16 / 57.32 / $0.72; Qwen3.5-4B 17.96 / 39.73 / $0.25; Qwen3-VL-8B 34.27 / 16.96 / $0.25; supervised NetVLAD++ (cross-dataset) 56.82 / 38.49. Only 3 matches, replays cause false positives, no latency reported, and the authors frame it as offline potential, not real-time capability. Qwen3-VL-8B missed kickoffs and shots.
- SoccerNet VQA 2026 top entries all used frontier/large VLMs: vitomeme 98.0%, a Gemini-3.1-Pro pipeline 97.6%, a Claude-based agent 96.0%, a Qwen3-VL LoRA multi-expert 95.0%. [2026 results](https://arxiv.org/html/2607.07320v1).
- GSR 2025 winner used LLaMA-3.2-Vision for jersey/role/team as autoregressive generation; Qwen2-VL also appeared. [2025 results](https://arxiv.org/html/2508.19182v1). Roboflow found a fine-tuned SmolVLM2 insufficient for jersey numbers and a small CNN classifier better. [Roboflow](https://roboflow.com/blog/jersey-number-recognition-for-sports).
- Related: DeepSport (Qwen2.5-VL-7B backbone) [arXiv 2511.12908](https://arxiv.org/pdf/2511.12908); MSUE (Qwen3-VL-32B best zero-shot on a soccer VQA set) [arXiv 2606.12106](https://arxiv.org/html/2606.12106); GRAZE zero-shot event localization [arXiv 2604.01383](https://arxiv.org/pdf/2604.01383); SoccerChat [arXiv 2505.16630](https://arxiv.org/pdf/2505.16630); SoccerMaster (CVPR 2026 oral soccer foundation model, code/weights "will be released", no license yet) [arXiv](https://arxiv.org/abs/2512.11016), [repo](https://github.com/haolinyang-hlyang/SoccerMaster).
- Licenses: Qwen3-VL Apache-2.0 (default 2 fps sampling) [repo](https://github.com/QwenLM/Qwen3-VL); InternVL MIT [repo](https://github.com/OpenGVLab/InternVL); SmolVLM2 Apache-2.0 [repo](https://github.com/huggingface/smollm); Molmo Apache-2.0 [repo](https://github.com/allenai/molmo).
- Verdict: no source shows a VLM inside a <2 s path. Use one offline for QA, hard-case labeling, and commentary-grounded validation.

### 2g. Camera calibration / field registration

- SoccerNet Calibration 2023 winner Sportlight 0.55 (ACC@5 × completeness; baseline 0.08): HRNetV2-w48 heatmaps for 57 keypoints + 23 lines, OpenCV calibration on point subsets, reprojection-error voting. [2023 results](https://arxiv.org/html/2309.06006v1).
- TVCalib (MIT, 54 stars) [repo](https://github.com/MM4SPA/tvcalib); No Bells Just Whistles (CVPRW 2024; DLT on learned keypoints; 61 stars) [repo](https://github.com/mguti97/No-Bells-Just-Whistles), [paper](https://arxiv.org/abs/2404.08401v1); PnLCalib (points + lines optimization; refinement lifted JaC@5 from 74.4 to 80.6 on SN test-center; **GPL-2.0-or-later**; 111 stars; pushed 2026-10-26) [repo](https://github.com/mguti97/PnLCalib). sn-gamestate lets you swap `tvcalib` / `nbjw_calib` / `pnlcalib`. GSR 2025 third place used PnLCalib + radial distortion + temporal smoothing; 2024 winner used a 74-keypoint ResNet50 with voting.
- Downstream: Field Converter (world-grounded player pose from broadcasts) [arXiv 2609.10498](https://arxiv.org/pdf/2609.10498); SoccerNet-v3D uses the PnLCalib keypoint detector [arXiv](https://arxiv.org/html/2504.10106.pdf).
- Basketball: no published NBA-grade model. Roboflow hosts a `basketball-court-detection-2` keypoint dataset [roboflow/sports](https://github.com/roboflow/sports); community repos: [basketball-perception](https://github.com/ianmparker/basketball-perception) (18-keypoint model, 4.04 ft median reprojection error; AGPL; brand new), [cs25m116](https://github.com/cs25m116/Basketball-Player-Detection-Tracking-Identification) (33 landmarks), [abdullahtarek/basketball_analysis](https://github.com/abdullahtarek/basketball_analysis) (197 stars, YOLOv8 court keypoints). "Inside the box" in soccer is solved; "inside the paint/arc" in basketball needs your own keypoint model.

### 2h. Player identification

- Jersey numbers: SoccerNet 2023 winner ZZPM 92.85% (multi-frame fusion aug + ensemble of SVTR/SATRN/NRTR/ASTER text recognizers, DBNet++ filtering) [2023](https://arxiv.org/html/2309.06006v1); 2024 report cites a two-stage CLIP approach at 0.78 tracklet accuracy [2024](https://arxiv.org/pdf/2409.10587); Koshkina CVPRW 2024 general framework 79.31% [paper](https://openaccess.thecvf.com/content/CVPR2024W/CVsports/papers/Koshkina_A_General_Framework_for_Jersey_Number_Recognition_in_Sports_Video_CVPRW_2024_paper.pdf); Grad CVPRW 2025 single-stage uncertainty-aware 85.62% tracklet-level [paper](https://openaccess.thecvf.com/content/CVPR2025W/CVSPORTS/papers/Grad_Single-Stage_Uncertainty-Aware_Jersey_Number_Recognition_in_Soccer_CVPRW_2025_paper.pdf). GSR 2025 winners: LLaMA-3.2-Vision (KIST), fine-tuned CLIP ViT-L/14 (lianyou). OCR backbones: PaddleOCR (Apache-2.0) [repo](https://github.com/PaddlePaddle/PaddleOCR), mmocr (default in sn-gamestate).
- Team assignment: roboflow/sports `sports/common/team.py` = SigLIP crop embeddings → UMAP (3D) → KMeans (k=2), goalkeepers by nearest centroid; k=3 for basketball incl. referees. [roboflow/sports](https://github.com/roboflow/sports), [Roboflow basketball post](https://roboflow.com/blog/identify-basketball-players). KIST 2025 clustered jersey colors and used cluster mean x-position for left/right side. Constructor 2024 trained OSNet team-ID on 111 uniforms.
- Re-ID: [sn-reid](https://github.com/SoccerNet/sn-reid) (MIT), [sportsreid](https://github.com/shallowlearn/sportsreid) (MIT, 27 stars, 2022, #2 on SoccerNet 2022 ReID, [arXiv 2206.02373](https://arxiv.org/abs/2206.02373)), 2023 ReID winner UniBw CLIP ensemble 93.26 mAP; tracklab's `prtreid`.

## 6. Streaming / infra

- Latency budget reality: classic HLS 20–30 s, LL-HLS 2–5 s, WebRTC 0.2–0.8 s; the packager alone adds 50 ms–4 s. "<2 s behind the stream" is achievable relative to the frames you receive, not relative to the stadium, unless you ingest SRT/RTSP/RTMP from the venue or LL-HLS. [Mux](https://mux.com/docs/guides/reduce-live-stream-latency), [Fora Soft latency](https://www.forasoft.com/learn/video-streaming/articles-streaming/latency-glass-to-glass-explained), [OTT engine](https://www.ottengine.com/blog/low-latency-live-streaming-sports).
- FFmpeg input flags that matter: `-fflags nobuffer`, `-flags low_delay`, small `-probesize`/`-analyzeduration`, `-rtsp_transport tcp`, HLS `live_start_index -1` (start at the newest segment) / `prefer_x_start`. [FFmpeg formats docs](https://ffmpeg.org/ffmpeg-formats.html), [RTSP example](https://hawxtech.net/measure-rtsp-camera-latency-for-a-factory-demo-feed.html). Pass these as `options={...}` to `av.open`.
- OpenCV `VideoCapture` on RTSP can take 5–15 s to first frame and buffers frames; use a GStreamer pipeline string or PyAV instead. [guide](https://industrialmonitordirect.com/blogs/knowledgebase/troubleshooting-gstreamer-rtspsrc-opencv-videocapture-latency), [Jetson alternatives](https://proventusnova.com/blog/gstreamer-alternatives-nvidia-jetson).
- PyAV: `HWAccel.create("cuda")` / `("videotoolbox")`, `hwdevices_available()`; needs an FFmpeg build with the hwaccel compiled in; a VideoToolbox H.265 raw-NAL decode failure was reported in 2025; one thread measured PyAV decoding 30 RTSP streams at ~20 FPS vs ~5 FPS for `uridecodebin` due to CPU threading. [CHANGELOG](https://github.com/PyAV-Org/PyAV/blob/main/CHANGELOG.rst), [discussion #1929](https://github.com/PyAV-Org/PyAV/discussions/1929), [GStreamer discourse](https://discourse.gstreamer.org/t/how-to-improve-cpu-thread-usage-in-gstreamer-decoding-vs-pyav-performance/4865).
- torchcodec: NVDEC decode to CUDA tensors (FFmpeg built with NVDEC required); set `num_ffmpeg_threads=0` for CPU parity with decord; live-stream (RTSP/HLS) support is undocumented — treat as file/URL-oriented until you test it. decord is Apache-2.0 but last pushed 2024. [torchcodec PyPI](https://pypi.org/project/torchcodec/), [issue #426](https://github.com/meta-pytorch/torchcodec/issues/426), [torchaudio NVDEC tutorial](https://docs.pytorch.org/audio/2.8/tutorials/nvdec_tutorial.html) (~2663 fps HW vs ~1492 fps SW on a 224p clip), [decord](https://github.com/dmlc/decord).
- GStreamer/DeepStream: NVDEC decode, batched `nvinfer` TensorRT, `nvtracker`; Python frame access limits in §1; DeepStream 9.0 had an `nvmultiurisrcbin` HLS regression. [forum](https://forums.developer.nvidia.com/t/ds-9-0-gst-nvmultiurisrcbin-http-https-stream-add-behavior-changed-live-hls-and-rtsp-over-http-now-broken/365925), [RidgeRun glass-to-glass on Jetson](https://developer.ridgerun.com/wiki/index.php/Jetson_glass_to_glass_latency).
- Batching that keeps latency low: decode on GPU, run the detector every frame at batch 1–2 (RF-DETR-B is ~6 ms on T4, so well under a 40 ms frame at 25 fps on a 4090-class GPU), pose on tracked crops every 2nd–3rd frame batched by person, ball detector on a crop, and the spotting head on a rolling feature buffer. Never batch across time for the provisional event path; only the "confirm" path may wait for a window. Keep everything on the GPU between stages ([Fora Soft playbook](https://www.forasoft.com/blog/article/real-time-video-processing-with-ai-best-practices)).
- Measure p50/p95 glass-to-glass with burned-in timecode or NTP-stamped audio tones. [Fora Soft](https://www.forasoft.com/blog/article/minimizing-latency-to-less-than-1-sec-for-mass-streams-315).
- Apple Silicon for dev: CoreML export of detectors runs on the ANE only at FP16/INT8 (FP32 falls back to CPU); YOLOv8n FP16/INT8 ~1.6–1.7 ms/img on M4 Pro ANE; a vendor M4 Max test got ~8 FPS on yolov11m-seg at 640 via MPS. [edge-ml-bench](https://github.com/AtomicAyush/edge-ml-bench), [Roboflow M4](https://blog.roboflow.com/putting-the-new-m4-macs-to-the-test/), [Ultralytics CoreML](https://docs.ultralytics.com/integrations/coreml). VideoToolbox decode via PyAV `HWAccel("videotoolbox")` (a hardware session is not guaranteed even if the codec is listed). Plan: ONNX Runtime with CoreML EP or PyTorch MPS on the Mac, TensorRT on Linux, same ONNX graphs.

## 7. Reference architectures (what vendors publish)

- SkillCorner (broadcast-only tracking): frame-by-frame detection/tracking, dynamic pitch calibration on the panning main camera, no data during close-ups/replays, extrapolation model for off-screen players; open sample of 10 matches incl. 29 3D joints per player. [SkillCorner](https://skillcorner.com/products/football/xy-tracking-data), [Medium](https://medium.com/skillcorner/a-new-world-of-performance-insight-from-video-tracking-technology-f0d7c0deb767), [opendata](https://github.com/SkillCorner/opendata).

- Sportlogiq: broadcast tracking for hockey; detection, team ID, re-ID, puck; slides at Edge AI & Vision 2023. [slides](https://www.edge-ai-vision.com/wp-content/uploads/2023/10/T1T09_Javan_Sportlogiq_2023.pdf), [tech page](https://www.sportlogiq.com/technology/).

- Pixellot: DeepStream SDK on Jetson Orin NX at the edge; multi-angle capture. [NVIDIA](https://blogs.nvidia.com/?p=67151). Veo: 2-lens 4K panoramic, ball-follow AI after upload; clips in ~30 s. [Veo](https://www.veo.com/en-us/article/the-road-to-simplicity-building-veo-go), [comparison](https://zone14.ai/en/blog/veo-vs-pixellot-vs-zone14-video-analysis-in-football-compared/).
- WSC Sports: ML tags plays on live feeds for highlights; "no unique hardware"; patents on "learning highlights using event detection"; no latency figures published. [WSC](https://wsc-sports.com/blog/news/lega-serie-a-utilizing-ai-technology-by-wsc-sports-to-create-real-time-highlights/), [patent](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10867212).
- Independent check: a 2025 validity study notes no published accuracy validation of commercial broadcast tracking for position/speed. [arXiv 2508.19477](https://arxiv.org/pdf/2508.19477).

What an open-source clone can replicate: the SkillCorner/Opta Vision single-broadcast-camera stack (detect → track → calibrate → pitch coords → events) is exactly what sn-gamestate + a spotting head is; GSR 2025 at 63.9 GS-HOTA is the open ceiling. What it cannot: multi-camera 3D skeletal tracking (Hawk-Eye, Second Spectrum) and anything during replays/close-ups, since the broadcast director controls what you see.

## Recommended v1 stack (one sport)

**Sport:** soccer, main broadcast camera. Reasons: SoccerNet is the only open benchmark with pass/shot/cross/throw-in labels on broadcast video at scale (77+22 games with 12 classes; FOOTPASS with 102,992 events carrying team and jersey), published winning methods with code (T-DEED 73.39 mAP@1; TAAD/DST under Apache-2.0), a working calibration stack (PnLCalib/TVCalib), a full GSR reference pipeline (tracklab), and challenge-proven detector/tracker choices (YOLOX/Deep-EIoU/OSNet). "First shot / first pass / first possession" is also the easiest sub-problem in soccer: kickoff is scripted (ball centered, two players, whistle), first possession is the kickoff team by rule, the first pass is the kickoff touch, and "shot" is a ball-velocity-toward-goal event you can confirm with calibration ("inside the box" = homography + 16.5 m line). Basketball is next (tip-off is equally scripted, but there is no public broadcast event dataset, NBA tracking data has been closed since 2016, and court calibration models are community-grade). Tennis is mechanically simplest (two players, static camera, serve = first event) but has almost no labeled broadcast data (TenniSet = 5 matches) and the "first point" is already on the scoreboard. Baseball and American football are the hardest from broadcast: constant camera cuts, pitch/snap occlusion, and community ball detection around 60%.

**Stack (licenses chosen for a commercial product; GPL/AGPL/NC items are reference-only):**
- Ingest: PyAV with `HWAccel("cuda")` on Linux / `("videotoolbox")` on Mac, `nobuffer`/`low_delay`/`live_start_index=-1`; own SRT replay rig for latency tests.
- Detection: RF-DETR (Apache-2.0) fine-tuned on Roboflow football-players + SoccerNet-Tracking boxes (NDA data, check terms); separate RF-DETR-nano/D-FINE ball head plus WASB-style crop refinement (MIT).
- Tracking: ARC-SORT (Apache-2.0) or BoostTrack++/OC-SORT (MIT) in pitch coordinates, OSNet re-ID (torchreid), GTA-style offline tracklet merge for post-hoc correction.
- Calibration: train your own keypoint+line model on SoccerNet-Calibration (Sportlight recipe: HRNet heatmaps + reprojection voting) or use TVCalib (MIT); PnLCalib (GPL-2.0+) only as an isolated process or for evaluation.
- Team/ID: SigLIP→UMAP→KMeans from roboflow/sports (MIT); jersey numbers via a small CNN/SVTR classifier on tracklets (PaddleOCR Apache-2.0 as a fallback), voting over the tracklet.
- Pose: RTMO via mmdeploy → TensorRT (Apache-2.0), run on the 4–6 players nearest the ball.
- Events, two tiers: (1) provisional, causal, <300 ms: rules on tracking state (possession change = ball within r of a new player's feet for k frames; shot = ball speed spike toward goal from inside/outside box; kickoff = whistle/centered ball + two players); (2) confirmed, 2–4 s: a TAAD/DST-style head (FOOTPASS, Apache-2.0) on X3D (Apache-2.0) player features, re-implemented rather than forked from T-DEED (GPL). Emit `provisional` then `confirmed`/`retracted` on a Redis Stream/NATS topic with stream PTS, wall clock, team, jersey, pitch x/y, zone.
- Offline QA: Qwen3-VL (Apache-2.0) over storyboards + Whisper commentary to audit missed/false events, never in the live path.
- Runtime: TensorRT FP16 on one RTX 4090/5090-class GPU; ONNX Runtime CoreML EP / MPS on the Mac with identical ONNX graphs; per-stream process, asyncio stage queues; Savant only if you later need >3 streams per GPU.
- Latency target: decode→provisional event ≤0.5 s on a pushed SRT feed; confirmed ≤3 s. Against public HLS you will be 10–30 s behind the venue regardless.

**Open items to resolve before building:** (1) SoccerNet NDA wording on commercial R&D (the HF-gated NDA is per repo and emailed to you); (2) whether training on CC BY-NC datasets (FOOTPASS annotations, SportsMOT, MultiSports) is acceptable for a betting product; (3) a real low-latency feed source, since none of the consumer services expose one.
